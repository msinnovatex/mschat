4. Architecture and Responsibilities

Use a server-first security architecture.

The browser communicates with the backend API for authenticated operations. The backend verifies the user's session and authorization before reading or modifying protected data.

The backend is responsible for:

- Registration and login.
- OTP verification.
- Session creation, validation, rotation, and revocation.
- Friend requests and friendship authorization.
- Message writes and server-authoritative timestamps.
- Message receipts.
- Conversation membership checks.
- Attachment authorization and upload coordination.
- Blocking and account status enforcement.
- Administrative operations.
- Usage aggregation and security logging.
- Browser push notification delivery.

Firebase RTDB stores application records and can provide suitable realtime primitives where the security architecture permits them.

Important realtime limitation

Do not give browser clients unrestricted Firebase access just to make realtime chat easier.

Because authentication uses a custom application session rather than Firebase Authentication, Firebase Security Rules will not automatically know which MS Chat user owns a request.

Choose and document a secure delivery architecture:

1. Authenticated, cursor-based polling through backend APIs as the initial reliable option; or
2. A separately secured realtime relay or managed realtime service when justified.

Optimize polling to minimize unnecessary Firebase operations. Do not create a permanent polling loop for every inactive conversation.

Use Firebase presence primitives directly only when client authentication and database rules genuinely authorize the intended operations. Otherwise, implement server-managed presence with expiration and stale-record cleanup.

Never claim WebSocket support if the deployment architecture does not actually support it.

7. Registration and Email OTP Verification

Implement the complete registration process.

Registration flow

1. User enters an email address and password.
2. Server validates the inputs.
3. Server creates a registration challenge.
4. Gmail API sends a numeric OTP.
5. User enters the OTP.
6. Server verifies the OTP and its associated challenge.
7. User completes their profile.
8. Server validates the declared age.
9. Server reserves a unique username atomically.
10. Server creates the account and session.
11. User enters the main dashboard.

OTP security

- Generate cryptographically secure random OTPs.
- Expire OTPs after approximately five minutes.
- Limit verification attempts, for example to five attempts per challenge.
- Add resend cooldowns.
- Apply rate limits by IP address, email, and relevant account or challenge.
- Invalidate superseded challenges where appropriate.
- Bind the challenge to the email and intended action.
- Consume successful OTPs atomically and exactly once.
- Store a secure OTP digest, preferably keyed with a server-only secret, rather than raw OTPs.
- Never log OTP values.
- Never accept expired, reused, or mismatched OTPs.
- Return generic errors where detailed responses would enable account enumeration.
- Handle Gmail API outages and delivery failures gracefully.
- Never create a verified account if the verification flow has not succeeded.

Do not claim email verification succeeded merely because the email was submitted.

Profile setup

Collect:

- Full name.
- Unique username.
- Date of birth.
- Optional profile picture.
- Optional biography.

Require users to declare that they meet the minimum age of 18, and enforce the date-based age check on the server. Do not trust a frontend-only age check.

Treat the date of birth as private information. Do not expose it to other users or include it in public search results.

8. Manual Authentication and Persistent Login

Do not use Firebase Authentication.

Implement secure application-managed authentication.

Password security

- Use a suitable password hashing algorithm such as Node.js "crypto.scrypt", with a unique random salt and appropriately configured parameters.
- Alternatively, use a reputable maintained password-hashing library.
- Never store plaintext passwords.
- Never return password hashes to the client.
- Validate passwords on the server.
- Implement rate limits for login attempts.
- Avoid revealing whether an email exists through detailed authentication errors.
- Require reauthentication for sensitive account-security changes where appropriate.

Session security

Use a cryptographically random session token delivered through a cookie with:

- "HttpOnly"
- "Secure" in production
- An appropriate "SameSite" setting
- A narrow cookie path and sensible expiration
- Server-side session validation

Store only a secure hash of the session token in the database, not the raw token.

Implement:

- Session creation.
- Session expiration.
- Session rotation when appropriate.
- Logout and session revocation.
- Revoke-all-sessions functionality.
- Session invalidation after password changes or account suspension when appropriate.
- CSRF protection for cookie-authenticated state-changing operations.
- Origin and request validation.
- Protection against session fixation.
- Reasonable idle and absolute expiration policies.

Persistent login requirement

The user must remain logged in after:

- Closing and reopening Chrome.
- Restarting their phone.
- Closing and reopening the PWA.
- Routine compatible website updates and redeployments.

The user should remain logged in until logout, session revocation, session expiry, account-security action, or browser/app data being cleared.

Use the persistent secure cookie for authentication. Do not store the session token or password in "localStorage" or "IndexedDB".

Routine deployments must not unnecessarily change the cookie name, session-signing configuration, or session schema. Use backward-compatible migrations and preserve valid sessions.

Do not store authentication state only in React memory. Restore the authenticated state by validating the secure session with the backend when the application opens.

Local storage rules

Use "localStorage" only for non-sensitive preferences, such as:

- Theme.
- Sidebar state.
- Non-sensitive UI preferences.

Use "IndexedDB" only for appropriate, bounded local data, such as:

- Encrypted message cache.
- Non-sensitive offline metadata.
- Supported cryptographic protocol state when the chosen protocol requires it.

Do not store plaintext passwords, reusable session tokens, or plaintext private keys in browser storage.

Explain the security limitations of browser-based cryptography and client-side storage.

Settings and logout

Provide a clear Logout button.

Logout must:

1. Revoke the current server-side session.
2. Expire the authentication cookie.
3. Clear in-memory authentication and decrypted message content.
4. Stop active subscriptions, polling, and presence heartbeats.
5. Remove temporary plaintext data and pending sensitive UI state.
6. Return the user to the login page.

Do not indiscriminately erase harmless preferences or cryptographic recovery material. Account deletion and explicit secure-data reset must be separate operations with clear consequences.

12. End-to-End Encrypted One-to-One Messaging

End-to-end encryption is a core requirement, not an optional UI feature.

All private message bodies and attachment contents must be encrypted on the sender's device before being sent to the backend.

Cryptographic implementation

Use a reputable, maintained implementation of an established secure messaging protocol, such as a suitable Signal Protocol implementation compatible with the intended web environment.

Do not invent a custom cryptographic protocol.

Before choosing a library, verify its current maintenance status, supported platform, license, security assumptions, and suitability for browser-based use.

Document the selected protocol and its limitations.

Required security properties

Where supported by the selected protocol, implement:

- Client-generated identity keys.
- Secure session establishment.
- Authenticated encryption.
- Forward secrecy.
- Post-compromise recovery.
- Key rotation and ratcheting.
- Message authentication.
- Replay and tampering detection.
- Identity verification.
- Key-change warnings.
- Secure initial and subsequent message delivery.
- Appropriate key backup, recovery, and device-loss behavior.

Private keys must never be uploaded to the backend in plaintext.

The backend may store public keys and the encrypted or public protocol material required by the chosen protocol. Any private protocol state must remain protected by the client-side security model.

Do not silently replace an established identity key without notifying the user.

Do not pretend a device-loss recovery mechanism exists until it is implemented and tested.

Message lifecycle

1. Sender composes a message.
2. Client encrypts the message for the intended recipient using the established protocol.
3. Backend authenticates the sender and authorizes the conversation.
4. Backend stores the encrypted payload with server-authoritative metadata.
5. Recipient retrieves the encrypted payload.
6. Recipient decrypts it locally.
7. Recipient sends an authenticated delivery or read receipt.
8. Sender sees the appropriate message status.

The server, Firebase database, R2 storage, and admin dashboard must not have a general capability to decrypt private messages.

Important limitations

Even with E2EE, the service may expose metadata such as participants, timestamps, message counts, delivery state, IP-related security logs, and conversation relationships. Minimize and document this exposure.

Browser-based E2EE has additional risks because the application JavaScript delivered by the server could be modified by a compromised deployment or malicious code. Do not claim that E2EE eliminates compromised-device or malicious-code risks.

Do not advertise the app as independently audited or fully secure without appropriate independent review.

Initial implementation gate

Before releasing encrypted messaging:

- Verify key generation and storage.
- Verify both users derive compatible secure sessions.
- Test successful encryption and decryption.
- Test incorrect keys, tampered payloads, replay attempts, and changed identities.
- Verify the backend cannot decrypt stored messages.
- Verify message contents never appear in server logs.
- Document any cryptographic feature not yet implemented.

If a safe, compatible protocol cannot be implemented with the available dependencies, report the blocker instead of substituting insecure homemade encryption.

- Hide the message from the requesting user's conversation view.
- Preserve the other participant's authorized view.
- Apply the change consistently across the requesting user's devices.

Delete for everyone
